# 赛博网友机器人开发计划

版本：2026-09-14-v31
主题：通用可观测告警统一生命周期与升级通知
状态：已完成

## 给 AI 的开发大纲

### 目标

将可观测指标产生的通用告警接入持久化生命周期、恢复检测、多级升级策略和异步通知。渠道告警继续使用现有渠道生命周期；通用来源通过独立来源适配器接入同一套升级策略，避免强行伪造 channel_id。

### 实现范围

- 新增通用告警生命周期领域类型和 PostgreSQL 表，来源由 `source_type + source_key` 标识，生命周期按 `tenant_id + agent_id + source_type + source_key` 隔离。
- 首个来源实现 `api_error_rate`，从安全聚合指标生成 active/resolved 生命周期；后续队列、模型成本和通知死信只需增加来源适配器。
- 通用生命周期复用 `AlertEscalationPolicy`，每次最多推进一级，成功入队后才持久化等级；失败、去重命中和恢复检测不得提前推进。
- Worker 维护循环周期评估启用 Agent 的通用告警，并沿用 BackgroundTaskService、NotificationDeliveryTaskHandler、Outbox 和租户/Agent 作用域。
- 可观测性 API 增加 Agent 作用域和通用生命周期列表；管理后台展示活动告警来源、状态、升级等级、首次发生与恢复时间。
- 保持 Secret 不出 API、日志、任务载荷、生命周期表和配置差异；配置仍通过注册表、校验、管理 API 与配置后台维护。

### 实际完成

- 已落地 `api_error_rate` 通用来源、Agent/租户隔离的内存与 PostgreSQL 生命周期仓储、恢复耗时和多级升级候选。
- 已接入 Worker 分钟级维护桶、PostgreSQL advisory transaction lock、通知任务幂等载荷和成功后升级等级持久化。
- 已提供生命周期 API、OpenAPI/TypeScript SDK 和管理后台筛选表格，并补齐关键单元测试。

### 关键设计

- 不修改已有 `channel_alert_lifecycles` 的 channel_id 语义；通用表保留 `channel_id` 为空的需求空间，但本阶段不复用渠道表。
- `ApiRequestObservation.agent_id` 可为空；缺少 Agent 归属的旧请求只参与租户仪表盘，不创建 Agent 级生命周期，避免猜测归属。
- 通知载荷只包含来源键、生命周期 ID、数值摘要、事件和升级等级；幂等键包含租户、Agent、来源、生命周期、事件、Adapter 和升级等级。
- Worker 只扫描当前可见且未归档 Agent，评估逻辑在应用层，数据库仓储只负责原子对账和等级更新。

### 验收标准

- API 错误率超过阈值时能创建或更新通用 active 生命周期；指标恢复后变为 resolved，并记录恢复耗时。
- 同一租户不同 Agent、不同租户同名来源互不读取；无 Agent 归属的指标不会错误归入任一 Agent。
- 升级策略、值班路由、幂等键和渠道告警保持一致；通知任务失败或未持久化不推进升级等级。
- Worker 维护循环可重复执行且只产生去重任务；API 和 Web 展示通用生命周期且不暴露 Secret。
- `uv run poe check`、Alembic 单头、Web lint/typecheck/test/build、`git diff --check` 全部通过。
