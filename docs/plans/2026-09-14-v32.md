## 给 AI 的开发大纲

### 目标

在 v31 通用生命周期基础上接入更多真实可观测来源，并补齐各类指标的 Agent 归属。当前 Agent 的仪表盘、生命周期、恢复检测和升级通知必须使用同一份隔离后的指标，未归属数据只参与租户运维统计，不得复制到任一 Agent。

### 实现范围

- 通用生命周期新增 API 延迟、智能体运行成功率与延迟、模型失败率与成本、任务积压与等待时间、通知死信来源；渠道失败继续由渠道专用生命周期负责，避免重复通知。
- PostgreSQL 聚合按 Agent 过滤：智能体运行直接使用 `agent_id`，模型调用通过所属运行关联，任务和通知只读取载荷中已持久化的稳定 `agent_id`；缺少归属的数据不进入 Agent 生命周期。
- 当前 Agent 的可观测仪表盘使用 Agent 级生效配置和指标，租户隔离、时间窗、阈值和成本冻结语义保持不变。
- 用纯应用层来源适配映射生成稳定的 `source_type + source_key`，后续新增来源不修改仓储生命周期规则。
- 管理后台为来源和告警代码提供中文标签，保留稳定技术标识用于排障，不显示正文、通知目标或 Secret。
- 沿用现有配置注册表中的阈值、管理 API 与 Schema 驱动后台，不新增只能手改的运行参数。

### 关键设计

- 渠道投递失败率只保留在仪表盘活动告警，不进入通用生命周期；渠道专用生命周期仍是该来源的唯一真相。
- 任务归属只接受持久化任务载荷中的 UUID 字符串；历史或系统级任务缺少 `agent_id` 时不猜测归属。
- 每个告警代码映射为独立来源键，同一来源的重复评估更新原活动生命周期，不同来源独立恢复和升级。
- 对象存储继续以 MinIO 为唯一实现和产品称谓，本阶段不引入 S3 或兼容后端。

### 验收标准

- 四类重点来源：模型失败率、模型成本预算、队列积压和通知死信均可创建、复用、恢复并参与多级升级通知。
- API 延迟、智能体运行 SLO 和任务等待告警同步接入，且渠道告警不会在两套生命周期中重复出现。
- 同租户不同 Agent 的运行、模型、任务和通知指标互不读取；无归属记录不进入任何 Agent 生命周期。
- 当前 Agent 仪表盘与生命周期使用一致的配置快照和指标作用域，Web 以中文展示来源、告警和单位。
- `uv run poe check`、Alembic 单头、Web 完整检查和 `git diff --check` 全部通过。
