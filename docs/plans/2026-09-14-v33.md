## 给 AI 的开发大纲

### 目标

在 v32 的多来源通用告警生命周期上补齐首次活动与恢复通知，使通用来源拥有与渠道告警一致的活动、升级、恢复闭环。渠道与通用来源必须通过同一个安全通知任务构造入口入队，保持幂等、Agent 隔离和 Secret 运行时解析。

### 实现范围

- 通用告警对账结果显式返回本轮首次活动、本轮恢复、当前活动和待升级生命周期，转移识别在仓储原子对账范围内完成。
- Worker 对首次活动、升级和恢复分别创建通知任务；首次活动与恢复使用当前 Agent 默认适配器，升级继续使用升级策略解析出的路由。
- 通用通知事件采用稳定事件名 `observability.alerts.active`、`observability.alerts.escalated` 和 `observability.alerts.recovered`，载荷只包含生命周期标识、来源、告警代码、等级、数值与时间摘要。
- 抽取渠道与通用来源共用的通知任务构造和入队入口，统一 `agent_id`、Adapter 引用、幂等键、超时与重试字段，不在任务中保存目标地址或 Secret。
- 通知时间线将通用首次活动、升级和恢复事件归类到现有活动、升级和恢复筛选，不新增只能手工维护的配置项。

### 关键设计

- 生命周期转移由内存与 PostgreSQL 仓储在一次对账中返回；PostgreSQL 继续使用事务级 Agent 锁，避免并发 Worker 重复判定。
- 每个通用生命周期和事件生成独立稳定幂等键；重复维护、并发维护和任务重试只复用原任务，不重复投递。
- 恢复通知受现有 `alerts.notification.recovery_enabled` 控制；通知总开关、适配器、目标、Secret、超时与重试继续由现有配置定义、校验、管理 API 和后台管理。
- 通用升级等级仍只在通知成功投递后推进；首次活动或恢复投递失败不得改变生命周期事实。

### 验收标准

- 每个通用生命周期首次变为活动时只创建一个活动通知，后续持续活动评估不重复创建。
- 每个已活动生命周期恢复时只创建一个恢复通知；关闭恢复通知配置时不创建，重新活动后可形成新的独立生命周期和通知闭环。
- 通用活动、升级与恢复任务均按租户和 Agent 隔离，任务载荷不含通知目标或 Secret，通知时间线可以正确分类。
- 渠道既有活动、升级、恢复通知行为不回归，并与通用通知共用任务构造入口。
