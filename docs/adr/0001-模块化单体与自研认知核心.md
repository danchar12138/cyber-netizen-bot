# ADR 0001：采用模块化单体与自研认知核心

> 状态：已接受
> 日期：2026-09-10

## 背景

项目需要同时承载管理后台、内部对话、异步任务、多渠道接入和持续演进的拟人认知能力。过早拆分微服务会增加分布式事务、契约协调和部署成本；让认知核心直接依赖 Web 框架、持久化框架或模型厂商 SDK，又会限制测试、回放与替换能力。

## 决策

- 首期采用模块化单体，API 与 Worker 作为独立进程部署，共享明确的领域和应用契约。
- 依赖方向为组合根/基础设施 → 应用层 → Domain/Cognition；核心包不反向依赖 FastAPI、SQLAlchemy、Dramatiq、MinIO SDK 或模型厂商 SDK。
- Domain 保存领域实体、值对象和无副作用规则；Cognition 保存自研认知状态机、上下文、记忆策略和策略门。
- 外部模型、数据库、对象存储、任务系统和渠道都通过 Protocol 或应用端口接入，由 Infrastructure、Adapters、API 和 Worker 实现或组装。
- 只有出现独立扩缩容、故障隔离、安全边界或团队所有权的明确证据后，才评估拆分服务；拆分不得改变领域语义。

## 结果

- 核心认知逻辑可以脱离网络和数据库进行确定性测试与回放，厂商和框架能够在外围替换。
- API 与 Worker 仍可独立扩容，但共享代码发布要求严格保持契约兼容。
- 架构边界由自动测试持续检查，新增依赖前需要明确其所属层级。

## 验证

- `tests/unit/test_architecture_boundaries.py` 使用 AST 检查 Domain/Cognition 的导入边界。
- Python 静态检查、单元测试和端到端测试共同验证组合根仍然可运行。
